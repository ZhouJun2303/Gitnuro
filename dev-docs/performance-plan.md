# AweGit 项目性能优化计划与实施记录（2026-11-13，对照 599049a5）

更新：2026-11-13。适用分支：`feat/dev`。代码核验基线：`599049a5`。本方案汇总现有日志、代码检查、已完成的优化和后续实施安排，重点是 Rust 后端及触发后端工作的前端刷新链路。

PERF-00—10 的代码优化和针对性回归已实施，新增 debug 对照与 release 场景测量见第 8 节。第 2、3 节保留原始日志与上一轮结果，不能与本次结果混作一组样本。此前的检查见 [后端性能检查](backend-performance.md)，复测命令统一维护在 [开发与发布](development.md#性能复测)。真实安装包的远端网络、整段界面等待和系统峰值内存尚无新测量。

## 1. 目标与实施约束

目标是减少用户一次操作触发的重复扫描、Git 子进程和后台轮询，让拉取、冲突处理和长时间使用后的刷新更快，同时保持界面可以滚动和点击。

- 仓库写操作继续按仓库排队；读取继续在工作线程执行。先减少重复工作，再依据基准决定是否增加并行。
- 保留自动贮藏、暂存区恢复、未跟踪文件保护、`.fakeignore`、附加工作树及外部 Git 操作的现有语义。
- 不用过期的“干净工作区”结果决定是否保护本地改动；不以丢弃监听事件换取更少刷新。
- 状态、refs、提交历史、流程检查点分别失效。没有变化时保留已有结果和前端对象；不通过 `JSON.stringify` 比较整份数据。
- 正式包体验以 release 构建复测。debug、小仓库和不同 Git 版本的数字分别报告。
- 试验仓库和本地结果放在 `.lab/`；可复用的种子脚本、测试和场景清单提交到仓库，不拿 AweGit 自身仓库做写操作实验。

## 2. 已核验的性能证据

### 2.1 计时口径

1. `cmd` 时间包含内部 Git 调用，不能把上层命令与子命令的累计耗时再次相加，也不能把累计调用耗时当作 CPU 时间。
2. 并发预览、监听和刷新可能重叠。端到端等待按时间区间计算，不能直接相加所有日志行。
3. `cmd operation_flow` 和 `web invoke operation_flow` 是同一次调用在后端、前端的两层计时。
4. 现有汇总主要提供次数、累计值、平均值和最大值，不能由平均值推导 p95。不同仓库和操作类型也不能混为同一基准。
5. 下文的正式包日志来自优化前的安装版本，不能证明当前源码打包后的性能。

### 2.2 正式包一次拉取：`mutate` 6072ms

来源：2026-11-13 的 `awegit-release.log`，主要证据在第 153—248 行；日志行号仅适用于此次核验的文件，轮转后按时间查找。`mutate` 约在 09:46:32.987 开始，09:46:39.059 结束。

| 项目 | 耗时 | 与 `mutate` 的关系 |
| --- | ---: | --- |
| 检查本地改动的 `status --porcelain -z --untracked-files=normal` | 216ms | 内部串行步骤 |
| 自动 `stash push --include-untracked` | 1205ms | 内部串行步骤 |
| `pull --no-autostash --rebase` | 2948ms | 内部串行步骤，包含网络获取和整合 |
| `stash apply --index` | 474ms | 内部串行步骤 |
| 上述四项之外的开销 | 约 1229ms | 算术余量，现有日志不足以精确分摊 |
| 操作后的 `workspace_status` | 378ms | 在 `mutate` 返回之后 |
| 两轮 `repository_refs` 和 `commit_log` | 累计 763ms | 在 `mutate` 返回之后，存在重复读取 |

后两轮 refs 分别为 140ms、137ms，历史分别为 245ms、241ms。第二轮历史于 09:46:40.295 完成，比 `mutate` 返回晚 1236ms；这段时间包含等待和其他工作，不能全部认定为可消除成本。

沙箱预览在 `pull` 执行期间发生：`init` 75ms、`read-tree` 155ms、`merge-tree` 34ms，另有配置和元数据读取。它有资源成本，但不能把这些耗时再加到 `pull` 上，也不能承诺去掉预览就能等量缩短等待。

代码确认：干净工作区仍会执行改动检查，但会跳过 `stash push`。有本地改动时才执行自动贮藏；这里的贮藏不是 `git add` 暂存。待优化的是检查与保存的成本，不是修复“干净工作区也贮藏”。

### PERF-00：补齐计时归因

入口：[后端计时](../src-tauri/src/perf.rs)、[Git 执行器](../crates/git/src/cli.rs)、[前端计时](../src/lib/perf.ts)、[命令与监听](../src-tauri/src/lib.rs)。

方案：为一次用户操作、后续刷新和子任务传递关联标识，记录单调时钟的起止、仓库标识、构建与 Git 版本；区分队列等待、操作前检查、保存本地改动、Git 主操作、恢复、流程收尾、状态读取和前端刷新。关联信息显式传入异步预览等子线程，避免仅依靠线程局部状态。前端保留事件实际发生时间，落盘时间另记。

验收：一次拉取可以画出时间区间并解释关键等待；同一调用的 `web`、`cmd`、`git` 可关联且不重复计数。沿用现有日志脱敏，不新增完整状态或文件内容日志；比较开启前后的开销，控制记录量。

### PERF-01：合并写操作后的刷新

入口：[后端 `mutate` 与 `read_status`](../src-tauri/src/lib.rs)、[前端状态与监听](../src/lib/shell/state.svelte.ts)、[`loadContext`](../src/lib/shell/history.svelte.ts)。

现状：`mutate` 已返回状态；前端随后加载上下文；操作期间积攒的 `repo-changed` 又触发 `workspace_status` 和上下文刷新。现有 `contextGen` 能阻止旧结果覆盖，但不能阻止后端重复计算。

方案：按仓库维护刷新中的请求、所需范围和数据版本，合并相同读取；`full` 覆盖 `status`，已返回且仍有效的状态直接使用。将监听事件序号与快照覆盖范围关联，延迟到达但已被快照覆盖的事件不再触发全量读取；无法证明已覆盖时补一次刷新。仅状态变化不重载提交历史，refs 变化再加载相关上下文。只在数据版本和请求参数一致时共享读取，写后不复用写前结果。

验收：没有外部并发修改的一次拉取只出现一轮必要的 refs、历史刷新，不因自身监听再读一次状态；操作期间或完成后的真实外部修改仍被发现。覆盖多仓库、多窗口、快速切换仓库、后台获取与失败路径，旧结果不能覆盖新状态。

### PERF-02：减少活动流程的重复检查点

入口：[`Session::refresh`、`reconcile_locked`](../src-tauri/src/flows.rs)、[`checkpoint`](../crates/git/src/flow.rs)、[流程窗口](../src/lib/FlowWindow.svelte)。

方案：以写操作完成和相关文件监听事件标记流程需要更新；同一仓库、同一版本并发请求共享一次检查点。正在写入时继续依靠操作事件，已结束流程继续使用保存的结果。冲突、等待等状态在无变化时复用最近检查点，保留低频兜底校验、窗口重新获得焦点校验，以及监听丢失后的恢复。轮询改成等待上次完成后再安排下一次，避免慢读取堆积。

验收：终态反复查询仍为零检查点 Git 调用；稳定冲突状态不再每秒无条件读取完整检查点。外部解决冲突、继续或中止操作后，事件正常时按当前约 1 秒响应目标更新；兜底间隔单独记录。最后一个冲突、待继续、待恢复贮藏与自动关闭行为保持正确。

### PERF-03：降低监听与忽略判断频率

入口：[仓库监听的 `classify_changes`](../src-tauri/src/lib.rs)、[`ignored_paths`](../crates/git/src/model.rs)。

现状：`ignored_paths` 已使用 `check-ignore -z --stdin` 批量处理，调用方也已排序去重。问题是大量批次，不能把“改成逐批调用”当作尚未实施的优化。

方案：先统计批次来源、路径数和同路径重复率，再合并同仓库相邻事件；持续事件流设置最大等待，避免无限延迟。对相同数据版本、相同候选路径共享进行中的判断；若增加结果缓存，明确处理嵌套 `.gitignore`、`.git/info/exclude`、全局忽略配置和 index 变化的失效。无法确认有效时重新查询；避免递归监视忽略目录产生无用风暴，但不能屏蔽其中已跟踪文件的变动。

验收：固定的编辑、编译产物生成和拉取事件序列中，调用批次明显减少，并报告前后次数；已有单批只调用一次 Git 的行为保留。忽略规则修改、被跟踪文件、重命名、附加工作树及监听溢出后的完整刷新均正确。

### PERF-04：优化自动贮藏前后的检查

入口：[`changed_paths`、`push`、`restore`](../crates/git/src/autostash.rs)、[`with_autostash`、Pull、Merge](../crates/git/src/ops.rs)。

方案：分别测量干净、少量已跟踪修改、大量未跟踪文件的检查、贮藏和恢复成本，统计重复扫描。评估能否把流程所需的改动信息与同一次可靠扫描合并，或采用正确性等价的检查方式。用于保护改动的判断必须在写队列内可靠验证；前端旧快照只用于显示。按路径贮藏、拆分获取与整合等策略仅在单独验证恢复语义后考虑，不能直接作为默认实现。

验收：干净工作区保持零 `stash push`；有改动时完整恢复 staged/unstaged 划分、未跟踪文件、重命名和删除，保留根目录未跟踪 `.fakeignore`。拉取、合并、变基、失败、中止和恢复冲突都可继续；未成功恢复前不能丢弃贮藏。报告不同场景中实际减少的扫描次数与 p50/p95，不承诺直接省掉全部 1.9 秒。

### PERF-05：批量读取冲突元数据

入口：[冲突详情](../crates/git/src/change.rs)、[检查点与提交对象](../crates/git/src/flow.rs)、[Git 执行器](../crates/git/src/cli.rs)。

方案：列出一次 `conflict_view` 所有进程，合并重复的提交解析、对象大小与内容读取；优先复用同一次读取结果，评估 `cat-file --batch-check`、`--batch` 或现有对象读取能力。按对象 ID 缓存不可变元数据，对 HEAD、index、工作区和变基状态采用版本失效。先减少往返，再决定是否保留长驻进程。

验收：同一场景的 Git 进程数比当前合并详情 13 次、变基详情 12 次减少，并报告实际值；对象内容、大小、二进制判断和冲突阶段一致。切换文件、进入下一轮变基和外部解决冲突后不显示过期内容。

### PERF-06：限制 blob 前缀读取

入口：[二进制探测 `blob_has_nul`](../crates/git/src/change.rs)。

方案：保留大于现有大小上限的处理规则；对需要探测的 blob 只保留最多 8192 字节用于判断，避免把整个输出收集成 `Vec`。优先评估对象流读取；若通过 Git 管道实现，明确剩余 stdout、stderr、退出状态和进程回收策略，不能在读到前缀后留下阻塞子进程。流式丢弃剩余输出只解决内存，应与减少传输的方案分开测量。

验收：覆盖文本、NUL 在前缀内、前缀外、接近 8MB 和超过上限的对象；保持现有前缀判断语义。峰值分配不随整个 blob 等比例增长；反复打开和取消不泄漏进程，错误结果仍可正确处理。

### PERF-07：冲突文件匹配改为线性处理

入口：[`checkpoint` 的 unmerged 条目解析](../crates/git/src/flow.rs)、[`reconcile_locked` 的轮次匹配](../src-tauri/src/flows.rs)。

方案：用路径到索引的映射合并 stage 1/2/3，保留输出顺序；轮次比较预建路径与必要对象 ID 的集合或映射，替代逐文件查找。仅优化已确认的嵌套匹配，不改变流程身份和轮次判定。

验收：10、100、1000 个冲突的结果与原实现一致，匹配次数接近输入条目数线性增长；重复路径阶段、增删冲突、连续变基中同名文件正确。耗时与 Git 进程成本分别报告，避免进程启动掩盖算法变化。

### PERF-08：解耦历史清理和分页

入口：[`history`、`prune`、`cleanup_known`](../src-tauri/src/flows.rs)、[流程窗口历史轮询](../src/lib/FlowWindow.svelte)。

方案：将保留期清理放到有间隔的维护步骤，避免每次 10 秒历史轮询都解析全部摘要；在摘要新增、结束或删除时更新目录索引或缓存，普通分页只读取所需记录。先改调度和重复解析，再根据记录规模决定是否引入持久索引。

验收：100、1000、10000 条历史时报告分页读取文件数、总分配和耗时；无变化轮询不反复解析全目录，翻页不执行全量清理。进行中流程不被删除；过期摘要和事件文件按保留期清理；坏记录、重启和分页顺序保持可恢复。

### PERF-09：控制预览后台成本

入口：[`Session::preview`](../src-tauri/src/flows.rs)、[`preview_at`](../crates/git/src/flow.rs)。

方案：先用相同种子仓库和本地远端对照预览开启、暂停执行时的总等待、磁盘与进程数，再决定优化幅度。现有 generation 检查会丢弃过期结果，但不等于停止后台计算；可按仓库限制并发、合并相同预览、在可安全回收的边界取消过期任务。沙箱复用须隔离对象、配置和工作树，不写真实 index。

验收：实际拉取和合并继续直接执行 Git，不因预览额外等待完成；重复预览不产生无界任务，过期结果不覆盖真实冲突与已结束流程。完成资源清理，并单独报告初始化成本和对前台的实测影响。没有收益证据时保留现有功能，不按日志简单相加宣布提速。

### PERF-10：区分网络长尾与本地性能

入口：[Git 执行器及网络配置](../crates/git/src/cli.rs)、[命令计时](../src-tauri/src/perf.rs)。

方案：将 TLS、认证、代理、超时等失败与正常 fetch/pull 分开汇总；本地远端用于比较代码改动，实际远端用于观察网络长尾。若问题重复出现，再分析具体网络条件和既有取消、重试行为。

验收：日志能区分网络等待、本地整合和失败收尾；保留可理解的错误与重试路径。60924ms 的历史失败作为网络样本，不进入本地合并优化收益计算。

## 6. 基准场景与验收方式

### 6.1 可复现的数据集

复用并扩展 `scripts/lab-seed.mjs`，所有实验写入 `.lab/`。生成量作为可调参数，避免每个普通测试都构建最大仓库。

| 本地远端与失败 | 固定 bare 远端的拉取/分支合并，另设失败样本 | 本地开销与网络长尾分离 |

### 6.2 测量与通过标准

- 每次记录提交、构建类型、Git 可执行文件和版本、数据规模、缓存状态及机器环境。Windows 优先用项目打包的 Git 2.56；系统 Git 2.38 不支持已有预览用到的 `merge-tree --merge-base`。
- 目标场景预热后至少采集 30 个同条件样本，报告次数、p50、p95、最大值、Git 进程数；首次打开和缓存预热后的结果分开。大规模场景可显式采用较少样本并标明限制。
- 拉取等写操作每次恢复到相同种子状态，使用固定本地远端；仓库恢复不计入操作耗时。保留实际远端的独立观测，不混入本地优化对照。
- 按 PERF 项的结构性标准验收：重复读取轮数、检查点次数、Git 进程数、读取字节、文件读取数或匹配次数确实降低；正确性回归通过后再报告时间收益。
- 提交前比较未修改路径的 p50/p95；出现稳定变慢、内存增长、事件积压或结果过期时查明原因，不能用平均值改善掩盖长尾退化。普通 CI 不断言易受负载影响的绝对毫秒数。
- 缓存键包括仓库/工作树、数据版本和请求参数；错误不永久缓存，不能跨写入复用旧读取。监听不可用或溢出时有完整重读路径。

### 6.3 功能与界面回归

界面当前已有虚拟列表、大合并分块、按帧更新滚动等实现。本计划把这些作为持续验收约束，不认定存在新的前端瓶颈；若计时显示主线程卡顿，再增加针对性优化项。

后端结果变化后，前端按字段比较并保留未变化对象；提交图、搜索索引、整表计算只随数据变化。大历史按帧延续计算，差异保留行数上限，自动换行时不高亮屏幕外的行。验证滚动、输入和点击，不能只看到 Rust 命令更快就关闭任务。

具体 Rust、类型检查、相关 UI 和手动基准命令统一见 [开发与发布：性能复测](development.md#性能复测)。写入相关测试沿用单线程执行，UI 只选择本次涉及的用例。若遇到既有 `locks::tests::writes_name_the_process_and_explain_how_to_release_the_file` 环境失败，应保留原始失败及基线复现；显式跳过只用于补查其余用例，不能声称全量通过。

改动 UI、弹窗或仓库状态时，补相关种子、场景与测试，验证命令同步到开发文档；新弹窗登记到 `src/lib/lab/scenes.ts`。没有 UI 改动时不跑全量 UI，也不为文档变更运行性能或功能测试。
