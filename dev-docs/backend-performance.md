## 已完成的优化

- [目录解析](../crates/git/src/model.rs)已有按仓库路径保存的缓存，但[操作流程](../crates/git/src/flow.rs)绕过了它。现在历史、流程、自动恢复和冲突元数据共用这个解析器；目录消失后仍会重新查询，附加工作树使用各自的 Git 目录。
- [流程刷新](../src-tauri/src/flows.rs)原来在读取完整检查点后才判断流程是否结束。现在在启动 Git 前排除 `completed`、`failed`、`aborted` 等终态；`conflict`、`waiting`、`running` 仍然读取当前 Git 状态，并保留读取后的并发检查。
- [冲突元数据](../crates/git/src/change.rs)读取 `MERGE_MSG` 和变基状态文件时，直接使用已解析的工作树目录，省去每个文件的 `git rev-parse --git-path`。没有缓存文件内容，因此外部解决冲突后仍能读到新状态。

## 第一轮发现的后续优先项

以下来自调用链和数据读取方式，尚未做大规模基准；不把它们算作本轮已解决的问题。

1. 活跃冲突流程的 `checkpoint` 和 `conflict_view` 仍需多个串行 Git 调用。合并详情本轮仍为每次 13 个进程；下一步可用批量对象读取合并元数据与对象大小查询，并合并同一仓库并发发生的相同读取。
2. `change.rs` 的 `blob_has_nul` 只检查前 8KB，但会先把允许范围内的整个 blob 读入内存。多个接近 8MB 的冲突版本会放大分配和管道传输，应改为有上限的前缀读取。
3. `flow.rs` 的检查点解析按文件在已有列表中逐一搜索；大量冲突时会出现平方级比较。`flows.rs` 中冲突轮次的文件匹配也有嵌套遍历，需要用大量冲突文件的场景验证后优化。
4. `flows.rs` 的 `history` 每次先清理全部历史摘要，再重新枚举和排序；流程窗口每 10 秒请求一次历史。长时间使用后应把保留期清理与分页读取分开，避免每次轮询读取整个历史目录。

Git 命令已由工作线程执行，仓库写入也已有独立队列。本轮沿用这两点；继续优化应优先减少重复工作和进程往返，再评估并行度。
